## Decided
- (2026-11-17, owner "3 bản UI lệch nhau") UI pack: the page is a signed zip (`scripts/ui-pack.mjs` -> Pages `website/ui/`) that the phone + parent app download and serve instead of the bundled page (`android/shared/UiPack.kt`, protocol "UI pack", flow `remote.md` 2.9b). Critique of the first design, and what changed because of it:
  - Ed25519 -> **ECDSA P-256 / SHA-256**: `java.security` has Ed25519 only from API 33 (minSdk 26); P-256 exists on every API and in Node `crypto` (DER signature both sides).
  - Code from the network runs with the LAN/relay tokens and the parent app's `KGApp` bridge = same trust as an APK: signature check is mandatory (a hijacked Pages account alone cannot push code), https only, no redirects, size caps, only whitelisted file names, every file hash checked, `ver` recomputed from the hashes (a manifest cannot lie about its content).
  - Key loss / leak: a lost key = phones keep the bundled page until an APK release carries new keys (an APK update is the only revocation). Mitigation built in: **two public keys baked in** (signing key + offline backup), `*.pem` git-ignored, `--init` prints where to back them up. Forks run `--init` to bake their own keys.
  - Replay / downgrade: `seq` (unix s) must rise AND stay >= `floor` (highest ever installed, kept when the cache is dropped). Freeze (host serves nothing) cannot be prevented; the bundled page still works.
  - Version skew: the page already degrades on old phones (missing state fields), but it also calls native things (`KGApp.*`, CSP origins, endpoints). So `minKid` (phone versionCode) **and a separate `minParent`** (the parent app's bridge), hand-set in `scripts/ui-pack.json`; the build refuses a value above `kg.code`. A pack the app does not fit is ignored.
  - Bad pack: signature does not catch a *valid but broken* page. So: keep `prev/`, a new pack is *pending* until the page reports `/ui/ok` after `boot()`; 3 index loads without it = blacklist + previous pack. Rollback of a published pack = publish a newer one (the seq rule forbids "going back"). `start.js` calls `uiPackBoot()` after `boot()` on purpose.
  - Cache corruption: re-verified (signature + hashes) when loaded after a restart; corrupt = dropped, previous or bundled. Written to a temp dir + rename. An app update drops the cache (the new APK's bundled page is at least as new; no build seq in the APK needed).
  - Offline: bundled page, nothing breaks. Home flavor has no INTERNET and no server: out of scope. Storage ~0.3 MB zip, ~0.9 MB per copy, 2 copies.
  - CSP / old WebView: headers come from the native server, not from the pack, so a pack cannot loosen them; a new external origin needs an APK release (raise `minKid`/`minParent` with it). The pack is the same JS as today (no new syntax), so old WebViews see nothing new.
  - Relay deploy order: relay first, Pages second (`scripts/deploy.sh`): a pack must never reach a relay that lacks an endpoint it calls. The worker still imports `ui/` at deploy (unchanged) and has no `/ui/pack.json`.
  - Not committed: `website/ui/` is git-ignored and generated by `build.sh` / `deploy.sh` (a 0.3 MB zip per UI change would bloat the repo). Same content = same `seq` (the build is idempotent).
  - Dev push: `POST /ui/push` on the phone has **no token**: the signature is the gate (a LAN stranger cannot make one; an old signed pack is refused by seq). Covers the kid phone only; the parent app gets packs from Pages.
  - Still open: the call screen (`call.html` + `rtc.js`) stays bundled while `call.js` (in the pack) could drift from it; a dev-push for the parent app; no pack delta (0.3 MB per UI change, fine).
